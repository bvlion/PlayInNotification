# 再レビューと通常の対話CLIの保存検証（承認待ち時点）

対象は [最新のChatGPT再レビュー](https://github.com/bvlion/PlayInNotification/pull/141#issuecomment-6186868075) と、新規インライン2件。初回・非対話試行の結果とは区別する。

## 修正と通常作業への影響

共通の `.codex/config.toml` を削除した。このファイルには担当数上限4件と有効化しか残っておらず、どちらも専用ランチャーに同じ指定がある。これで通常作業の上限と有効化状態もユーザー設定・クライアント既定値へ戻る。

CLI 0.162.1の `config/read` の実測は、通常起動ではagents未設定、専用ランチャーのagents指定を渡した場合はenabled=true・max_concurrent_threads_per_session=4だった。5担当の同時実起動や、クライアント・管理設定由来の上限解除を確認したという意味ではない。

上限の指摘には [返信・resolve](https://github.com/bvlion/PlayInNotification/pull/141#discussion_r4281210314) 済み。

## ユーザー承認の正当性

承認者を推測せず、workflow.jsonのauthorizedApproverをnullで追加した。ユーザーが明示するloginとAPI解決した不変ユーザーIDを保存する。未設定では本番開始・問題確定・完全自動化を受理しない。

承認候補はIssue #140のコメントをAPIで取得し、投稿者のlogin/ID・Userであること・代理投稿の有無・承認種別・対象バッチ/版/SHA-256を確認する。本文・投稿者・編集日時等の証跡を保存し、進行直前に再確認する。OWNER表示だけや、管理役がユーザー指示を転記した同loginのAI投稿は承認の証拠にしない。

モデルによる模擬12ケースで、本人の直接投稿の正例と、未設定・第三者・同login別ID・Bot・同ユーザーの代理投稿・別Issue・別版・別スナップショット・別承認種別・本文編集・API取得不可の拒否を確認した。正例は架空データであり、現実の本番承認を受理した試験ではない。実際の再レビューコメントのAPIメタデータも確認したが、PR上のAI代理投稿であり、本番承認へ転用しない。

現実の承認者はユーザーの指定待ち。[承認者スレッド](https://github.com/bvlion/PlayInNotification/pull/141#discussion_r4281210716) は返信したうえで未resolveにしている。既存の確定168問をこの追加手順で再選定することはない。

## 保存失敗の原因と対話環境の試行

[公式仕様](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots) では、workspace-writeでも.gitとworktreeのポインターが参照するGit管理領域は読み取り専用である。前回のneverでの失敗は、この領域へのindex.lock作成拒否だった。

今回はcodex execではなく、PTY上の通常のCodex CLI対話セッションを起動した。実行履歴でもsource=cli、gpt-6.1-sol / medium、workspace-write、approval_policy=on-request、network_access=falseを確認した。承認先はuserと明示した。フルアクセス、自動承認、追加ディレクトリ、永続ルール、個人設定、認証は変更していない。

最初に模擬検証の文脈を渡して読み取りだけを行わせ、その後の入力は「続きお願い」だけとした。管理役は作業ツリーが空であることと専用ブランチを確認し、問題データを含まない19行の状態JSONを作成・再読込・差分提示した。git addは同じindex.lock拒否（exit 128）となったが、今回は同じコマンドの対話承認画面が出た。

現在の要求は `git add -- operations/kanji/verification/interactive-save/state.json`。画面には「Yes, proceed」「同じprefixを今後も許可」「No」が表示されている。外側のエージェントは承認を入力していない。ユーザーには次の選択肢を提示している。

- 今回の模擬状態1ファイルのadd/commit、専用ブランチへのpush、Issue #140への模擬進捗コメント1件について、操作ごとに今回のみ承認して検証を続ける。
- 承認せず、承認要求までの観測結果を保存して検証を保留する。

承認要求の実行ID・ツールの失敗出力・模擬状態の全文とSHA-256は `interactive-save-check.json` に残した。テスト本体の状態ファイルは未追跡で、CLIの承認待ち対象として保持している。この報告のcommit/pushを外側のエージェントが行っても、対話管理役自身の保存成功には含めない。

## 目的の成立状況

| 要素 | 現在の結果 |
| --- | --- |
| 管理役へ「続きお願い」で模擬作業を進める | 対話CLIで作成・差分提示・Git承認要求まで実行済み |
| 管理役自身で途中保存を完了する | ユーザーの操作承認待ち。commit/push/Issue投稿は未実施 |
| 管理役自身が保存した状態から新規セッションへ復帰する | 上記の保存が未完了のため、一連として未検証 |
| 外側の検証者が保存した状態からの新規復帰 | 初回検証で確認済み。今回の一連成功の代替にはしない |
| 本番開始・問題確定・完全自動化 | 承認者未設定・各承認未取得のまま停止 |

「管理役に続行を依頼するだけで、途中保存と中断後の再開まで行える」という目的全体は、現時点では成立を確認できていない。通常の対話承認によって残りの工程を実行できるかは、ユーザーの選択後に検証する。

実際の50問は未作成・未監査。問題TSV・アプリ・既存テスト・確定168問は維持している。運用設定と文書のみのためGradleのローカル再実行は不要。シェル構文、TOML/JSON、差分の整合を確認する。
