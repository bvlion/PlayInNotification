# 再レビューと通常の対話CLIの保存・新規復帰検証

対象は [最新のChatGPT再レビュー](https://github.com/bvlion/PlayInNotification/pull/141#issuecomment-6186868075) と、新規インライン2件。初回・非対話試行の結果とは区別する。

## 修正と通常作業への影響

共通の `.codex/config.toml` を削除した。このファイルには担当数上限4件と有効化しか残っておらず、どちらも専用ランチャーに同じ指定がある。これで通常作業の上限と有効化状態もユーザー設定・クライアント既定値へ戻る。

CLI 0.162.1の `config/read` の実測は、通常起動ではagents未設定、専用ランチャーのagents指定を渡した場合はenabled=true・max_concurrent_threads_per_session=4だった。5担当の同時実起動や、クライアント・管理設定由来の上限解除を確認したという意味ではない。

上限の指摘には [返信・resolve](https://github.com/bvlion/PlayInNotification/pull/141#discussion_r4281210314) 済み。

## ユーザー承認の正当性

承認者を推測せず、workflow.jsonのauthorizedApproverを初期値nullで追加した。その後、ユーザーがこの会話で本人承認者をbvlionと明示したため、`GET /users/bvlion`でUser・ID `24517539`を確認し、今回の模擬保存・復帰検証完了後に登録した。承認者の指定は本番開始・問題確定・完全自動化の承認ではなく、各承認はnullを維持する。

承認候補はIssue #140のコメントをAPIで取得し、投稿者のlogin/ID・Userであること・代理投稿の有無・承認種別・対象バッチ/版/SHA-256を確認する。本文・投稿者・編集日時等の証跡を保存し、進行直前に再確認する。OWNER表示だけや、管理役がユーザー指示を転記した同loginのAI投稿は承認の証拠にしない。

モデルによる模擬12ケースで、本人の直接投稿の正例と、未設定・第三者・同login別ID・Bot・同ユーザーの代理投稿・別Issue・別版・別スナップショット・別承認種別・本文編集・API取得不可の拒否を確認した。正例は架空データであり、現実の本番承認を受理した試験ではない。実際の再レビューコメントのAPIメタデータも確認したが、PR上のAI代理投稿であり、本番承認へ転用しない。

承認者の未指定は解消した。既存の確定168問をこの追加手順で再選定することはない。現実の本番承認コメントを受理する試験は行っていない。

## 追加到着した保存位置コメントの指摘

[保存コメントの投稿者・履歴確認の指摘](https://github.com/bvlion/PlayInNotification/pull/141#discussion_r4281226446) も通常の公開Issue投稿で発生し得るため対応した。マーカーや日時だけで採用せず、GitHub APIで実投稿者IDと既存のwrite / maintain / admin権限を確認する。問題確定の本人承認と進捗投稿は分け、書込権限を確認したAI代理投稿は進捗保存に使用できる。

保存先ブランチを信頼済みローカル設定に固定し、記録commitがそのリポジトリ・ブランチ先端と同じか祖先かを確認する。古い正当commitが示されても先端の正本状態を読み、古い状態へ戻さない。分岐・API失敗・状態不整合や無断の承認者変更では停止する。復元JSONだけで承認者や保存先の信頼設定を変更しない。

模擬11ケースで正規投稿と正規だが古い記録の先端復元、第三者の偽マーカー・権限取得不可・別ブランチ・別repo・不明commit・分岐・投稿者ID不一致・承認者の無断変更・不整合の拒否を確認した。実APIでは現在の進捗投稿者のIDとadmin権限、Issue #140、正当な古いcommitから保存先先端へのahead関係を確認した。証跡はcheckpoint-origin-check.json。第三者名義での実投稿や実データ巻き戻しは行っていない。

## 権限の違いと保存失敗の原因

元セッションの実行履歴は`danger-full-access / never`であり、ユーザーの`/permissions`のFull Access設定と一致した。一方、先行検証用に別起動したCLIには、検証者が`-s workspace-write`と`-a never`または`-a on-request`を明示していた。したがって、前回の保存失敗は元セッションのFull Accessでの失敗を示すものではない。実行条件の違いを十分に区別できていなかった。

今回、復帰用に権限・承認引数を省いた新規対話CLIも実起動した。その実効値は`workspace-write / on-request / network_access=false`だった。ユーザー設定のsandbox_mode・approval_policyは未設定で、approvals_reviewerはuser。元セッションの会話中の権限状態は、この別起動プロセスに引き継がれなかった。ランチャーも権限引数を渡していないため、新規起動後の実効権限を確認する必要がある。個人設定、元セッション、永続ルール、認証は変更していない。

[公式仕様](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)ではworkspace-writeの.git保護はworktreeのポインター参照先にも及ぶ。実際の失敗は共有Git管理領域のindex.lock作成拒否（exit 128）だった。network_access=falseではGitHubの名前解決・API接続も失敗した。対話CLIで同じコマンドの今回限りの承認を受けると、どちらも実行できた。元セッションのFull Accessそのものを使った管理役の保存一連は今回は試していない。

管理役自身のツール呼び出しで以下を完了した。外側の報告用commit/pushを成功の代わりにはしていない。

承認待ち中に外側の検証者が報告と保存コメント検証手順を53321be・4e8dc2cで更新していたため、管理役は開始HEADとの差を検出して一度停止した。外側の検証者が既知の更新を説明し、管理役が差分・親子関係・空の作業ツリーを再確認して続行した。sourceCommitは検証開始時511e8faの履歴として維持した。これは権限以外の追加介入であり、完全無介入の一言だけの実行を確認したとは扱わない。

## 新規管理セッションによる復帰の実測

保存した管理役を終了し、履歴をfork/resumeしない別の通常CLI管理セッションで、難読漢字の検証という文脈と「続きお願い」を渡した。保存commit IDや状態の内容は入力に渡していない。新管理役はローカル状態JSONをコピーせず、GitHub APIからIssue #140の保存コメントを発見した。

新管理役自身が、投稿者bvlion / ID 24517539、権限APIの同IDのadmin権限、リポジトリ・Issue・PR専用ブランチ、記録commitと先端の同一関係を確認した。GitHubの先端からworkflow.jsonと模擬状態を取得し、コメントの不変性と先端を再確認した。API読み取りにも今回限りの通常承認を使用した。

復元した状態は版1、進捗「対話環境での途中保存」、担当なし、未解決0件、userApproval=pending、productionStartApproval / automationApproval=null。本番setup_only・未開始を維持した。取得した状態のSHA-256は`5cddf0685732950bae9c171577c40de46eee21aadc01dd474700c2a8c9abb6d3`で、保存時の実バイト列と一致した。別の問題スナップショットは存在せず、その検証を行ったとは扱わない。

## 最終確認で見つかった追加レビュー2件

[primary worktree起動の指摘](https://github.com/bvlion/PlayInNotification/pull/141#discussion_r4282124270)は、通常のcloneのcodexブランチで再現した。事前用意されたworktreeの.gitはディレクトリの場合があり、ファイル必須条件が起動を拒否していた。既存のgit rev-parseによるリポジトリ確認とcodexブランチ条件を維持し、ファイル形式の条件だけを削除した。新しい起動機能は追加していない。

ローカルのlinked worktreeと一時cloneのprimary worktreeで、CLIスタブに指定モデル・推論・担当上限が渡ることを確認した。mainブランチは拒否する。修正前のprimary codexブランチの拒否も再現済み。実際のCodex Remote環境は未検証であり、スタブの起動確認を実モデル起動と混同しない。証跡はinteractive-save-check.jsonのlauncherWorktreeCheck。

[本人承認の代作防止の指摘](https://github.com/bvlion/PlayInNotification/pull/141#discussion_r4282124280)は未解決である。今回の実際のCLI進捗投稿のメタデータから、管理役が本人と同じアカウントで投稿できる以上、login/IDとnullのapp欄だけでは承認の作成主体を機械的に分離できないことを確認した。承認者の特定による第三者の拒否は実装済みだが、人間本人の承認を管理役が代作できない技術的な保証まではない。今回の模擬進捗投稿を本番承認と扱ってはいない。

この保証を追加するには、A：本人承認者の資格情報にアクセスできない環境・別の資格情報で管理役を動かす、またはB：管理役が生成・改変できない署名等の承認経路を設ける、のようなユーザー判断が必要になる。Aは認証と実行環境の分離、Bは新しい承認機構の設計が必要である。どちらも管理役が本人の資格情報・署名鍵を読める構成では保証が破れる。今回は追加の仕組み・機能を作らない指示に従い、独断で変更せずスレッドを未resolveとして報告する。
